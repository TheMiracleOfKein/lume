# Lume v0.7.0: pre-release check

Branch `feat/v0.7`, diff `v0.6.6..HEAD` (23 files, +2203 / -16). `SyncBackends.kt` was uncommitted during the first review; it is committed now (8b1a2d8). The second review at the end of this file reads HEAD (397d2df).

Method: nothing was built, compiled, unit-tested, run on an emulator or sent to a live server. The findings come from reading the code: the full diff, the new sync files and the changed reader files in full, and the call sites of the new APIs. Compile errors below are read from the code, not from a compiler.

## What changed

**Mechanisms**
- Sync between devices (Settings → Sync). Two places: a folder picked with the system picker (SAF tree URI), or a WebDAV server. Each device writes one file, `lume-sync-<deviceId>.bin`, and reads all the others.
- `SyncCodec`: gzip, and optionally AES-256-GCM with a PBKDF2 key and a new salt per file. The passphrase is off by default.
- `SyncMerge`: each record gets a change time against the last saved state, then one winner per record.
  - Newest change wins for the library, categories, read marks, bookmarks, links and per-title settings.
  - Furthest chapter position wins for chapter progress.
  - "Continue" goes to the title read last.
  - Removals are kept as tombstones for 180 days.
  - A "wiped database" guard skips the removals when the library is empty but the last sync knew a library.
- `SyncRepository.apply`: writes the changes to Room (packs and categories first, the rest in one transaction).
- `SyncWorker`: periodic (every 0, 1, 6, 12 or 24 hours; 0 means manual only) and once five seconds after app start. Folder sync needs no network; WebDAV needs one.
- Sync settings live in the private DataStore (`lume_private`). It is excluded from cloud backup and from Lume's own backups.
- Reader: page slider in the bottom bar (mirrored for right-to-left); orientation lock (auto, portrait, landscape); own brightness; colour filters (sepia, grey, warm); e-ink mode (grey, more contrast, no page-turn animation); webtoon auto-scroll; webtoon tap zones; share and save page from a new top-bar menu.

**Screens, menus, buttons, animations**
- Settings → Sync (new page in the Sync group, found by search): Off / Folder / WebDAV chips, folder link, WebDAV dialog (URL, user, password), passphrase dialog, five interval chips, "Sync now" with a progress bar and a status line.
- Reader top bar: new share icon with a dropdown (Share page, Save page).
- Reader bottom bar: page slider (replaces the page label when the chapter has more than one page); play/pause for auto-scroll (webtoon only, takes the place of the settings button there). The top bar still has the settings button.
- Reader settings sheet: own brightness (switch and slider), colour filter chips (four), e-ink switch, orientation chips (three), auto-scroll speed slider and tap-zone switch (webtoon only).
- Animations: section expands and fades in on the Sync page; progress bar while syncing; auto-scroll glides frame by frame.

## Serious problems found (first review)

1. `data/sync/SyncMerge.kt:81-89` with `data/sync/SyncRepository.kt:128-130`: a sync with no saved state (first sync, a fresh install, a new folder) stamps every local record as changed now. Titles another device removed earlier then come back on every device, because "now" beats the older tombstone.
   Status: fixed for this case in a604506 (`bootstrap`). The fix has a new side effect: Second review problem A.
   Fix: in `stamp`, when a record is not in `previous`, use `changedAt = 0L` (or the record's own `createdAt`/`updatedAt`) instead of `now`. Keep `now` only for records that differ from the saved state. Add a test: first sync against an older removal keeps the removal.

2. `data/sync/SyncRepository.kt:129` with `data/sync/SyncMerge.kt:136-139`: the wiped guard fires when the library is empty, so a user who removes every title on one device gets them all back at the next sync. `SyncMergeTest.kt:120-125` asserts the same rule, so the test passes while the bug is there.
   Status: partly fixed in a604506 (a removal-all with other records left works). Still fails when nothing else is left: Second review problem C.
   Fix: decide "wiped" from the database itself (for example, the database file was just created or is empty), not from an empty library. Update the test to match.

3. `ui/screens/ManageViewModels.kt:428-429` (`saveSync`): when the backend, the folder or the WebDAV URL changes, the code calls `app.sync.reset()`. That includes turning sync Off. The next sync then treats every record as new (problem 1), so titles removed on another device while sync was off come back.
   Status: fixed in a604506 (`reset()` removed; `saveSync` only clears the old error).
   Fix: do not reset the saved state. It describes this device's own database and stays valid when the place changes. Remove the call and the `reset()` method if nothing else uses it.

4. `data/sync/SyncCodec.kt:50-51` with `data/sync/SyncRepository.kt:137-138`: a truncated or damaged encrypted file raises the same error as a wrong passphrase, and the error stops the whole sync on every device until someone deletes the file by hand. No data is lost, because the error comes before `apply` and before any write.
   Status: partly fixed in a604506: a damaged file is skipped when another device's file decodes. Not done: the header check, and a damaged file that is the only other file still reports "wrong passphrase" (Second review, worth a look).
   Fix: store the ciphertext length (or a checksum) in the header, so a damaged file can be told apart from a wrong key. Skip a damaged file and say so in the status. Keep the abort for a real passphrase mismatch.

5. `ui/screens/ReaderEffects.kt:76` and `:80`: `window?.attributes = window.attributes.apply { ... }`. `window` is `Window?` (from `activity?.window`), so `window.attributes` is a call on a nullable receiver and does not compile.
   Status: FALSE ALARM. The build and lint pass (per the user). The right-hand side runs only when `window` is non-null, so no change is needed.
   Fix: in both places use `window?.let { w -> w.attributes = w.attributes.apply { screenBrightness = ... } }` (the `onDispose` one with `BRIGHTNESS_OVERRIDE_NONE`).

6. `ui/screens/settings/SyncSettings.kt:117-131`: five interval chips in one `Row`. Each `ChoiceChip` (`ui/components/SettingsControls.kt:122-152`) has 12 dp padding on each side and no line limit. On a 360 dp phone, with the page and card insets, each chip has roughly 30 dp for its text, so "Вручную" and "Manual" break mid-word.
   Status: fixed in ac5fb78 (`FlowRow`, the `weight(1f)` is removed). Not measured on a 360 dp device.
   Fix: put the interval chips in a `FlowRow` (two lines), or use a menu. Check on a 360 dp device after the change. (Estimate from the code, not measured.)

**New serious problems**

A. **First sync loses local edits, and two devices never converge.** `data/sync/SyncRepository.kt:124` (`bootstrap = previous.isEmpty()`), `data/sync/SyncMerge.kt:89` and `:97` (records with no history get time 0), `data/sync/SyncMerge.kt:151-152` (on a tie, the first candidate wins, and the own copy is first).
   A change made on A before its first sync (a category, a per-title reader setting, a tracker status) loses to B's older copy of the same record, which has a real time. This is data loss through sync, and before a604506 it did not happen. Also, when two devices first-sync the same record with different data, both sit at time 0, each keeps its own copy, and they never agree.
   Fix: a record with no history should lose only to a removal, not to a live copy. Among live copies the newer time wins; on an equal time, every device picks the same copy (for example the larger JSON text). Add tests for both cases (step 44 and step 45).

B. **A record that fails to apply is removed everywhere at the next sync.** `data/sync/SyncRepository.kt:270-393` (`guarded` swallows the failure), `data/sync/SyncRepository.kt:149-153` (the state written is the merged view, which still has the record live), `data/sync/SyncMerge.kt:101` (a live record missing locally becomes a removal stamped now).
   Example: a SQLite error (full disk, a failing insert) on B. B's state keeps the record as live, so at the next sync B sees it missing, writes a removal at now, and A and every other device delete it. Before a604506 a failure stopped the sync before the state was written, so this could not happen.
   Fix: write the state from what was actually applied, or keep failed keys out of the "missing" check. Add a unit test for a failed apply. Not testable by hand in a reasonable way.

C. **Removing every title can bring them back.** `data/sync/SyncRepository.kt:123` with `data/sync/SyncMerge.kt:146-148`. When no collection holds anything after the removals (no categories, no reading progress, read marks, bookmarks or title settings: for example titles that were added and never opened), `looksWiped` is true. The state is dropped, no removals are recorded, and the other devices' titles come back on A and then on B. `SyncMergeTest.kt:137-145` asserts this rule, so the test passes while the bug is there.
   The guard only matters when the database is lost while the state file survives. The state file is in `noBackupFilesDir`, which is cleared with the app data, so a reinstall or clear-data already starts with no state.
   Fix: drop the guard, or limit it to a real database loss (for example a marker written by this install). Change the test to match. Check with step 46.

D. **Page turns and auto-scroll cancel each other (webtoon).** `ReaderScreen.kt:524-529` (page-turn collector: `animateScrollBy`, or `scrollBy` in eInk), `ReaderScreen.kt:540-562` (glide: `scrollBy` every frame). The volume keys send to the same flow (`ReaderScreen.kt:274`).
   Both use the default scroll priority, so each new scroll cancels the other. The glide cancels a page-turn animation within a frame. That cancellation (a `CancellationException`) ends the `pageTurns.collect` coroutine, so later taps and volume keys do nothing until the reader is reopened. The fix in 397d2df only handles the glide side. This comes from reading Compose's scroll code; it has not been run. Confirm with step 34 (start auto-scroll, tap the bottom third twice).
   Fix: pause the glide while a page turn runs (a flag or a mutex the glide checks), and make the collector keep running after a cancelled turn.

## Worth a look

- `data/sync/SyncRepository.kt:121-139`: a wrong passphrase on one device is not reported when another device's file decodes (for example a plain file from before the passphrase was set). The sync then writes an encrypted file with the wrong key and reports success. No data is lost, but the mismatch is hidden.
- `data/sync/SyncRepository.kt:139`: when the only other file is damaged and the passphrase is set, the sync reports "wrong passphrase". Finding 4's header check is still needed for the correct message.
- A damaged file that is skipped gives no notice in the status line. Add a count of skipped files.
- `data/sync/SyncRepository.kt:152-153`: the sync file is written before the state. A crash in between leaves the state older than the file. Low risk.
- `data/sync/SyncMerge.kt:157-162` and `:109-112`: "restart the chapter from the top" does not sync back. Furthest wins over a newer, lower position; only a tombstone resets it. The comment says a newer change resets it. Either fix the code or the comment.
- `data/sync/SyncMerge.kt:120`: a device offline for more than 180 days can bring removed titles back, because its live copy is re-published once the tombstone expires. Old files of retired devices (reinstalls) are never deleted and keep contributing. Consider deleting the file of a device that has not written for 180 days.
- `data/sync/SyncRepository.kt:155` and `:164-167`: the state file is written in place, not through a temp file and rename. If it is unreadable at start, `loadState` returns an empty state and the sync behaves like a first sync (finding A). Fix: write to a temp file and rename it; stop the sync when the file exists but cannot be read.
- `data/sync/SyncRepository.kt:268-307`: one record that cannot be decoded no longer aborts the sync (fixed in a604506), but it is then removed everywhere (problem B). Fix B first.
- `data/sync/SyncRepository.kt:273-278`: source packs from the shared place are installed on other devices. Whoever can write the folder or server can add a source. Consider asking first, or limiting it to the official index.
- `data/sync/SyncRepository.kt:149`: the device model is written into every sync file. With the passphrase off, reading history, page bookmark notes and the device model are plain text in the folder or on the server. The sync page does not say so in plain words. Add that line.
- `ui/screens/settings/SyncSettings.kt:198`: the WebDAV dialog accepts `http://`, so the password goes over the network unencrypted. Fix: accept https only, or warn.
- `data/sync/SyncBackends.kt:55-64` (committed in 8b1a2d8): the fallback deletes the device's own file before the new one is created. If creating the new file fails, the file is gone until the next sync. Some providers rename the new file to "name (1).bin", which leaves duplicates. Fix: create and write the new document first, then delete the old one.
- `data/sync/SyncBackends.kt` WebDAV `write` (PUT): a dropped connection can leave a truncated file. See finding 4.
- Restores: a cloud backup or a Lume backup restore writes records as changed now (the same effect as first-sync finding A), so removals made elsewhere after the backup are undone.
- Removing a title on one device keeps its reading progress there and on the other device (same as a manual removal before v0.7). Check that "Continue" on the other device still reads correctly (step 5).
- Device ids: `sync_device_id` is in `noBackupFilesDir`. The code comment says device transfer skips that folder. Confirm with a real device transfer (step 24).
- `ui/screens/ReaderSettingsSheet.kt` (colour filter row): four chips with `weight(1f)` and 12 dp padding. "Тёплый" or "Сепия" may break on a 360 dp screen. Check in Russian (step 43). Still open.
- "Newest wins" uses each phone's clock. A phone with a wrong clock can win every merge. Mention in the release notes.
- Fixed since the first review (397d2df): the reader's page total is hidden with the page number off (`ReaderChrome.kt`); auto-scroll stops when the mode changes (`ReaderScreen.kt:143`); a failed page save deletes its empty row (`ReaderEffects.kt:116-121`).
