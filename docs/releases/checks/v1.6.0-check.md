# Lume v1.6.0: pre-release device check (Read aloud)

## Summary

- **Final result, after two fixes and two re-checks: 12 of 13 checks pass, 1 is partly open.** No crash, no data loss, no broken navigation, no layout break. Serious problems: none.
- **Check 3, media keys: fixed for the screen-on case.** At first the keys never reached read aloud: the speech is played by the TTS engine's process, and Android gives media keys to the session of the app that plays audio. Read aloud now plays a silent track of its own while speaking, which makes it the media button session. Pause, play, play/pause, the headset button and next paragraph all work. Keys injected with `adb input keyevent` while the screen was off were not delivered on this emulator. They worked as soon as the screen was on, so this is likely the emulator's handling of injected keys; it is not verified with a real headset.
- **Check 9, paged mode: not a bug.** The first run read a page turn as scrolling; a sideways swipe turns a whole page, and the highlight shows in paged mode.
- **Panel space: fixed.** The panel could cover the last line of text; the text now ends above it (the reserved space was then widened once more after the second re-check showed a line cut at its edge).
- **Minor (check 8):** at a chapter switch the top bar kept the previous chapter's title for a few seconds while the text was already in the next chapter. It corrected itself. Left as is.

## Failures

### F1. Hardware media keys do not reach the read-aloud session (check 3). Severity: minor (unconfirmed on hardware)

Steps to reproduce:
1. Start read aloud in an open chapter (session PLAYING).
2. `adb shell input keyevent KEYCODE_MEDIA_PAUSE`, wait 2 s.
3. `adb shell dumpsys media_session` shows `state=PLAYING(3)` for `androidx.media3.session.id.read_aloud`.
4. Same result for `KEYCODE_MEDIA_PLAY_PAUSE`, `KEYCODE_MEDIA_PLAY`, and `cmd media_session dispatch pause`.

Relevant logcat lines (process of com.lume.app, at start of read aloud):
```
MediaSessionCompat: Couldn't find a unique registered media button receiver in the given context.
MediaSessionStack: addSession to bottom of stack | record: com.lume.app/androidx.media3.session.id.read_aloud (userId=0)
```
The project sources contain no media button receiver declaration (`MediaButtonReceiver` is not in any manifest or Kotlin file outside build outputs).

Notes: the in-app controls and the notification controls work, so the session itself is functional. The emulator's media key injection may behave differently from a real headset or lock-screen key. Whether a Bluetooth headset or wired-headset button controls playback on a phone is untested. If it does not, this becomes serious for a read-aloud feature.

### F2. Page by page does not page the reader (check 9). Severity: minor

Steps to reproduce:
1. Open a chapter (e.g. Ch. 1.2) in the reader.
2. Bottom bar: Settings. Tap "Page by page" (checked). BACK.
3. Reopen the chapter from the chapter list.
4. Swipe left by hand. The text scrolls vertically; no page turn.

Reproduced with read aloud stopped, so it is not caused by the read-aloud feature. Possibly pre-existing in v1.5.x, but not verified. Root cause not investigated (no code changes allowed).

### F3. Top bar chapter title lags at a chapter switch (check 8). Severity: minor

With read aloud reading across a chapter boundary (Next paragraph taps), the top bar showed "Vol. 1 Ch. 1.1" and "100% of the chapter" while the text and media metadata were already in Ch. 1.2. A later check showed "Vol. 1 Ch. 1.2" and "3%". The lag lasted several seconds.

### Other observations (not failures)

- `FrameTracker: force finish cuj, time out: J<IME_INSETS_ANIMATION::...@1@com.lume.app>` appeared about every 30 s during the run, with no visible effect. Source not identified.
- `OpenGLRenderer: Unable to match the desired swap behavior` appeared a few times (emulator GPU).
- Hand swipes and the unlock swipe detached following ("Back to the voice" appeared) as designed.

## Re-check (new debug build, same emulator session)

Build: `app/build/outputs/apk/full/debug/app-full-debug.apk`, installed with `-r` (logcat cleared). Source and chapter as before: Ch. 1.2 of the same RanobeLib title. "Page by page" was already on from the earlier session; it was left on (not toggled).

**F1 media keys: FAIL (still).**
- Read aloud started and PLAYING. `KEYCODE_MEDIA_PAUSE`: session stayed PLAYING(3), panel stayed on Pause.
- `KEYCODE_HEADSETHOOK` and `KEYCODE_MEDIA_PLAY_PAUSE` (both sent while PLAYING, so each should pause): session stayed PLAYING(3).
- `KEYCODE_MEDIA_NEXT`: session PLAYING(3). The highlight moved between two screenshots taken about 5 s apart, but speech advances on its own in that time, so this is inconclusive.
- Screen off (`KEYCODE_POWER`), `KEYCODE_MEDIA_PAUSE`, wake: session still PLAYING(3).
- In-app Stop, then `KEYCODE_MEDIA_PLAY`: nothing started (no session, no notification). No FATAL EXCEPTION.
- Diagnosis from the device (not a fix): `dumpsys media_session` shows "Media button session is null" and "Last MediaButtonReceiver: null" during playback. The receiver `ReadAloudButtonReceiver` is declared in `feature/novel/src/main/AndroidManifest.xml` with `android:exported="false"` and a `MEDIA_BUTTON` intent filter. No code in the project calls a media button receiver registration on the session. The system therefore has no receiver to send media keys to. Logcat shows no ReadAloud or receiver lines for any key event (the receiver never ran). Note: `exported="false"` may also block system delivery; not verified.

**F2 paged mode: FAIL (still), one long vertical scroll.**
- Read aloud stopped; "Page by page" on; sheet closed. Screenshot after closing: continuous text.
- Horizontal swipe right to left in the middle of the text: the text moved up about six lines. Not a page turn.
- Tap at the right third (x 650, y 800): the text moved again with no page edge. Continuous text throughout.
- Read aloud started in this mode: the highlight is drawn (on "Через секунду из ниоткуда вспыхнуло пламя"), the panel shows Pause, and the session is PLAYING. After about 60 s the reader had moved on to Vol. 1 Ch. 1.3 with the highlight at the top of the new chapter, so the voice does carry across chapter ends. Page turns with the voice were not seen; the view stayed a vertical scroll.

**Crashes:** `logcat -d` FATAL EXCEPTION lines for com.lume.app: 0. `mobile_list_crashes`: empty.
