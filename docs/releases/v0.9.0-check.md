## Failed

### F1. Two archives with the same file name show each other's pages (serious: wrong chapter content)

Cause (read from code): `LocalEngine.pagesFromArchive` unpacks to `cache/local_zip/n_<file name without extension>`, and `ArchiveReaders.extractImages` skips any destination file that already exists. Two archives with the same base name (`04.cbz` in two series, or `01.cbr` and `01.cbz` in one series) and the same inner file names at the same index share one cache folder, so the second one shows the first one's pages.

Repro (reproduced on the emulator):
1. Import `Test Series` (it contains `04.cbz`, red/green/blue pages). Open its chapter 04 once so the pages are unpacked.
2. Add a second series `Dup Series` whose `04.cbz` has 2 yellow pages named `page1.png` and `page2.png` (same names as in Test Series).
3. Open Local > Dup Series > chapter 04.

Expected: 2 yellow pages. Actual: red and green pages from Test Series 04 (`11-dup-series-04.png`).

Note: `Other Series/01.cbz` (magenta, cyan, entries `o1.png`, `o2.png`) does not collide with `Test Series/01.cbr`; it displayed correctly (`10-collision-other01.png`). Only identical inner names trigger it, but real comic archives often reuse names like `001.jpg`, so it is likely to happen.

Suggested fix for the fix agent: key the cache folder on the archive's full path and last-modified time (as the CBZ download cache does), not on the base name.

## Possible bug spots from code reading (not all tested)

- `LocalImporter.copyFile` returns early when the destination exists and is non-empty, so re-importing a file that changed under the same name keeps the old content without any message.
- `LocalEngine.firstImageOf` returns the first cached file that is not a `.part`, without checking that it is a complete image. A cover written by a failed render stays broken until the file's mtime changes.
- `PdfRendererPool.render` allows bitmaps up to 2000 px wide and 16000 px tall (about 128 MB of ARGB). A PDF page with an extreme aspect ratio could run out of memory.
- In webtoon mode, `ReaderTallPage.originalPath` returns null for PDF pages, so very tall PDF pages are drawn as one bitmap with no slicing. A bitmap above the GPU texture limit may not draw (blank page). Not tested.
- `LocalEngine.coverFor` renders PDF covers with `runBlocking` inside `toSummary`, which runs on the IO dispatcher for every series in `getHome` and `pageSeries`. A large library of PDFs could block IO threads for a long time on first open.
- `readerPageBytes` (save page) sends `lume-pdf://` URLs through `imageLoader.execute` and re-encodes to PNG, so a saved PDF page is a re-rendered PNG, not a file. Not tested.
- `ArchiveReaders.open` maps `UnsupportedRarVersionException` from junrar, but a corrupt RAR5 throws a generic `RarException` that is shown as raw text (see minor findings).
- `ZipArchiveReader` opens the ZIP central directory on the reader thread for a whole archive. Fine for normal chapters; large archives (a few hundred MB) were not tested.
