## Minor findings

### M1. No notification for watched folder scans unless the permission was granted elsewhere (minor)

The watched folder flow never asks for `POST_NOTIFICATIONS`. Only the "Auto-check library" switch asks. On a fresh install, `FolderScanWorker.notifyNew` returns before `notify()` when the permission is missing, so a scan that finds a new chapter is silent. Setting-related docs (DEVICE_TESTING) expect the notification.

Repro:
1. Fresh install, Settings > Library and updates > Add a watched folder, pick a folder with a new chapter.
2. No notification appears. The chapter is copied.
3. Grant notifications for Lume (or turn Auto-check library on and allow). Tap Scan now with a new chapter in the folder: "Library updates / 1 new chapter" appears.

### M2. Watched folder rows and the interval chips do not line up with the rest of the group (minor, visual)

In the Russian screenshot the folder label starts about 12 px (at 1080 px width) left of the other rows' text, and the four interval chips run closer to the card edges than the other content. Nothing overlaps or clips in portrait or landscape.

### M3. DEVICE_TESTING.md names a status text that the UI does not show (minor, doc)

`docs/DEVICE_TESTING.md` says a lost folder "shows 'Access lost' with 'Reconnect'". The UI text is "Access to this folder was lost. Reconnect to scan it again." (`watched_unavailable`). Either the doc or the string should change.

### M4. Code style nits (minor)

- `AppContainer.kt`: `val libraryChapters =LibraryChapters(...)` is missing a space.
- `LibrarySettingsPage.kt`: `android.text.format.DateUtils` import is placed in the middle of the `androidx.compose` imports.
- `ManageViewModels.kt`: `folderName(...)` label for the folder is taken from the tree URI (shows "Download/LumeWatch"), which is fine but worth a look if a nicer name is wanted.

### M5. System notices in logcat (not Lume)

`Unexpected CPU variant for x86_64` (emulator), `Job didn't exist in JobStore` (WorkManager, after a one-time scan), and `carrierVvmPkgAdded` are system or library warnings. Not Lume exceptions. Noted only because they appeared during the run.

## Possible bug spots from code reading (not reproduced)

- Re-add or reconnect keeps old copies without comparing them. `Remove` deletes the ledger rows (`deleteImportedFilesFor`). After re-adding the same folder, `LedgerDiff.needsCopy(null, ..., destExists = true)` returns false, so a file that changed while the folder was removed is not copied again. The same happens after Reconnect to a different tree.
- Remove while a scan runs: `removeWatchedFolder` does not take the scanner's `Mutex`. A running `import()` can call `record()` after the delete and leave `imported_files` rows for a removed tree. `setWatchedFolderScanned` then updates nothing (harmless).
- "Scan now" uses `ExistingWorkPolicy.KEEP`. If a scan is already running when a folder is added, the new request is dropped. The running worker read `watchedFolders()` before the add, so the new folder waits for the next Scan now or the next periodic run (none if the interval is Off).
- `LocalImporter.copyImages`: a chapter folder that gains some images is not counted as a new chapter (`added == images.size`), so no notification for it.
- `FolderScanner.scan` treats any non-security exception as "try again next time" and returns null. A folder removed from the device is therefore silently skipped forever, with its `lastScanAt` not updated and no "unavailable" flag.
